## 一、议题一：AI售后（客诉自动化）

### 1.1 业务现状：链路长、人岗错配、渠道碎片

会议对现状的描述可以归纳为一条链路和三个结构性问题。

**客诉链路**：终端用户（广义C端，包含小进口商等使用中的B端客户）→ 经销商/分销商（多为"二传手"，直接转发）→ 品牌方（分流处理，跨部门指挥驻点工程师）→ 工厂（疑难问题终点）。根据合作模式不同，涉及三方到五方。

**三个结构性问题**：

第一是**信息损耗与追踪困难**。每多一层"二传手"就多一次信息衰减，当前依靠微信、邮件等碎片化渠道流转，没有统一工单系统，进度无法追踪，客诉优先级在各方 KPI 里都被边缘化。

第二是**人岗错配**。品牌方、分销商、工厂三方处理客诉的都是缺乏产品专业知识的文员，技术问题由非技术人员沟通，需要跨部门反复确认，时间成本极高。小团队里甚至是销售兼做售后，而销售的 KPI 导向天然让售后被忽视。Pony 的判断很准确：流程冗长只是表象，核心症结是人岗不匹配。

第三是**信息孤岛风险**。Nandy 点出了一个关键隐患：如果分销商拿着工厂配发的易损件自行消化了售后，信息流就在分销商那一层断掉了，品牌方和工厂拿不到底层数据。这一点会上没有给出解法，但它直接影响后面"大数据预测备件"能否成立。

### 1.2 终端用户的诉求边界

会上对齐的诉求范围比"报修"要宽：使用咨询（问一问）、维修保养、以及受西方 DIY 文化影响的**自行维修指导**。这意味着智能体不只是工单分发器，而是要能基于说明书和历史客诉，直接给出操作级的指导内容（文字、图片、视频、后续的 3D 动画）。这也是说明书议题和售后议题能融合的根本原因。

### 1.3 核心决策的逻辑拆解

**（1）接入起点：接管品牌方售后邮箱**

这是整场会议最关键的 MVP 判断。Pony 的理由有两条：海外用户习惯发邮件，强推 App 注册登录会成为落地绊脚石；邮件是品牌方现有的、成熟的渠道，接管它不需要改造终端流程。Nandy 一度主张终端直连体验最佳，Pony 以落地复杂度驳回，Nandy 退而提出"品牌方代为录入终端信息"的折中。最终双方从对立走向"双轨并行"：接入现有渠道是绝对起点，新渠道作为兼容项。

Yang Meng 补充了成本视角：每多接一个渠道（邮件、App、社交媒体）就多一份 token 消耗和维护成本。基于此砍掉了社交媒体渠道（交由品牌方自行监控），邮件被确立为主流渠道。

**（2）二维码网页端：从"一物一码"到"固定码 + 拍照识别"**

这一段讨论的演进过程值得记录，因为它是典型的"技术理想向实操妥协"：

- 李晓兵提出网页端二维码作为轻量入口，支持拍照和 AI 实时互动，解决邮件异步往返的时效痛点；
- Pony 提出"一客一码"、二维码自动映射设备信息，用户只填故障症状；Yang Meng 确认本质是序列号作为链接参数；
- Nandy 对实操提出质疑：一物一码在产线批次贴码环节风险大（贴错、找不着码）；
- 最终方案：**在现有产品标签旁增设一个固定售后二维码，扫码进入表单后由用户拍照上传标签，AI 自动识别 SKU/序列号并匹配订单与供应商**。

这个方案的妙处在于把"动态二维码"这个产线难题，转化成了"静态二维码 + 图像识别"这个纯软件问题。李晓兵确认无需复杂视觉算法，在现有基座上组合即可。颗粒度上，二维码可以细化到产品系列或型号，但不需要到单品。

网页端的天然缺陷是关闭后历史记录丢失，对此敲定的策略是**引导用户留邮箱或下载 App**，用轻量入口承接流量，用留存痛点做 App 转化。

**（3）客诉处理的三级升级机制**

AI 先自行判断并解决 → 信息不全则向用户追问 → 仍无法判断则转品牌方内部售后 → 再不行转工厂销售，由工厂内部闭环。工厂对平台而言是"黑盒"，品牌方只管拿结果。一期平台只对接工厂销售端，不介入工厂内部流转，也不给工厂售后开管理端权限（Pony 明确拒绝了 Yang Meng 的提议）。

这个设计的实质是：**AI 做前置过滤，人工做兜底；品牌方掌握主动权，工厂作为后端技术支持**。客诉管理负责人明确归属品牌方销售团队。

**（4）知识来源：品牌方提供**

Yang Meng 多次追问售后知识应由品牌方还是工厂销售提供，Pony 拍板售后场景的知识必须由品牌方提供，具体做法是把历史客诉记录喂给智能体。这里有一个值得注意的认知错位：Yang Meng 关心的是"知识从哪来"这个产品设计细节，Pony 关心的是"先把议题边界控住"。会议记录显示这个问题在说明书议题里才得到部分回应（工厂上传中文草版、知识库可相互验证）。**实际上售后知识至少有三个来源：品牌方历史客诉、工厂的产品资料/说明书、以及平台跨品牌沉淀的通用经验，会上只明确了第一个。**

**（5）B端后台：PC 网页端 + 邮件互通**

Pony 最初建议品牌方用邮件抄送 + 周报看板，不专门开发；Yang Meng 和李晓兵倾向开发网页入口。最终 Yang Meng 拍板 PC 端，理由是知识库上传、环境配置、联系人录入等办公操作需要电脑。品牌方的诉求被 Nandy 和 Pony 概括为"初期配置 + 定期看仪表盘"的甩手掌柜模式，中间过程全权交给 AI。Yang Meng 建议 B 端入口采用带对话框的智能体形态，从单向填表升级为双向对话。

**（6）灵活上下游链路：按订单邀请制**

Yang Meng 提出摒弃固定层级链条，品牌方可按订单邀请对应的下游销售商或工厂人员加入，实现该商品的全链路实时感知。Pony 进一步把这个邀请权下放给工厂销售，让一线销售自主决定是否拉内部工程师或研发介入。这是一个低耦合的协作模型，类似"按需拉群"，避免了预设组织架构的僵化。

**（7）从售后成本到品牌资产**

Yang Meng 提出的几个类比很有传播力：24 小时响应 + 远程视频指导像"美团外卖"拉开体验差距；全链路透明是品牌方"24 小时反馈"承诺的背书；售后数据沉淀是工厂端的"大众点评"。这把售后从被动"擦屁股"转为了主动营销资产，也是 Pony 认可的差异化空白点。

**（8）语言策略**

现状是工厂端普遍用英语服务，牺牲了终端消费者的母语体验。方案是二维码表单让用户自选语言，AI 把服务端英语实时转为消费者母语，人工沟通弥补理解偏差。首轮文字，视频延后，沟通重在解决障碍而非追求翻译精准。人工服务被反复强调为不可替代，AI 降本但不省人工兜底。

**（9）数据沉淀与备件管理（二期以后）**

Nandy 指出传统换件周期长达半个月（备件重制 + 运输）。路线图是：客诉数据积累 → 智能体分析高频故障件 → 向工厂建议提前备货，甚至随订单把备件前置到品牌方/分销商处（用空间换时间）→ 智能体接管免费配件进销存，按客诉记录自动扣减并预警余量。Pony 补充了跨品牌知识迁移：A、B 品牌的售后经验可以为 C 品牌生成易损件备货清单。全员共识是**当前卡点在数据冷启动**。

### 1.4 我对售后议题的几点深入分析

**风险一：信息孤岛和"大数据预测"是互相依赖的。** 如果分销商在自己那层消化掉大部分简单客诉（这恰恰是工厂配发易损件的目的），那么平台沉淀的数据只有疑难杂症，样本有偏，高频故障预测就会失真。建议：即便分销商自行处理，也应通过极轻的方式（比如扫同一个二维码点一下"已处理"）把事件打点回平台，否则二期的备件预测没有数据基础。

**风险二：邮箱接管的技术边界被低估了。** 会议把"接管邮箱"视为最轻量方案，但实际涉及：IMAP/Graph API 对接、多轮邮件线程合并为同一工单、附件（照片/视频）解析、AI 自动回复的放行阈值（哪些可以自动发、哪些必须人工审）、以及品牌方邮箱安全授权。这些都是一期必须做扎实的部分。

**风险三：知识来源只定了一半。** 品牌方历史客诉是案例库，但没有产品结构知识（爆炸图、零件编号、安装步骤），AI 无法给出 DIY 级的维修指导。这部分知识在工厂手里，恰好是说明书议题要处理的材料。两个议题在知识库层面必须打通，否则售后 Agent 的回答深度上不去。

**风险四：人工兜底的分工尚未落到人头。** "品牌方内部售后"在很多客户那里就是那个被反复提到的文员或销售，AI 把流程解放了，但升级到人工时仍是同一批人。需要在 B 端后台把"谁接升级工单"配置化，并给出 SLA 提醒。

**风险五：Nandy 对扫码便捷性的疑虑没有被正面回答。** 用户面对的实际动作是"找到码 → 扫码 → 选语言 → 拍标签 → 描述故障"，五步里任何一步掉队都会回流到邮件。建议 demo 阶段就做真实用户的扫码测试。

## 二、议题二：AI说明书生成

### 2.1 现状流程与痛点

现状链路：工厂制作中文说明书 → 业务翻译（多为非专业译者）→ 品牌方套模板排版 → 多轮人工流转。痛点有四个层面：

流程层面，多方流转繁琐且全靠人工。专业层面，Pony 以健身器材为例，译者缺乏行业知识导致译文不专业，还要再找母语人士二次校验，隐性成本高。成本层面，Pony 以美国品牌进军欧盟为例，面临多语种选择和高昂翻译费用，企业往往只准备少数语种。合规层面，Yang Meng 指出说明书兼具法律合规与消费者服务双重属性，语种缺失会直接影响海外市场的合规和服务。

### 2.2 目标流程

工厂（或品牌方）上传中文基础资料 → 云端智能体按品牌方模板自动生成目标语言说明书文本 → 生成 3D 安装动画视频（Nandy 明确视频说明书只需三维动画，不需要实拍）→ 品牌方确认 → 交付工厂。人工只做最终审核，解放工厂和品牌方的工程师、美工等人力。

### 2.3 市场划分与发起端

Pony 把需求划分为两类市场：**存量市场**（已有图纸/说明书，需要多语言化或规范化）和**增量市场**（新产品开发，从零生成）。发起端包含工厂和品牌方两类，Pony 建议将两类客户群融合进同一平台以简化流程。

### 2.4 功能延伸：从静态说明书到动态交互

Pony 提出把 AI 视觉识别融入安装环节：用户拍照，AI 自动匹配配件与对应安装步骤。这把说明书从静态文档升级为交互式指导，并且与售后场景的"拍照上传标签"复用的是同一类能力。

### 2.5 我对说明书议题的几点深入分析

**合规属性决定了"人工确认"不能是走过场。** 健身器材这类产品在欧盟（机械指令/CE、EN 957 等）、北美（UL、ASTM F2276 等）有明确的说明书内容要求：安全警告的措辞、符号、字号、必须包含的章节。AI 生成时应内置目标市场的合规检查清单，而不只是翻译。这也是产品差异化的机会：卖的不是翻译，是"合规的多语言说明书"。

**术语库是专业性的根基。** Pony 抱怨的"译者不专业"本质是缺乏行业术语一致性。建议每个品牌/品类维护术语表（中文 → 各语种，含禁用译法），生成时强制约束，审核时高亮术语偏离。这个术语库同时服务于售后 Agent 的多语言对话。

**3D 安装动画是整个方案里技术不确定性最高的部分。** 文本生成和多语言翻译是成熟能力，但从图纸自动生成 3D 装配动画，取决于工厂能否提供 3D 模型（STEP/SolidWorks 等）。如果只有 2D 图纸或照片，自动化程度会大打折扣。建议 demo 阶段明确输入物的最低要求，先用"有 3D 模型的产品"跑通，不要把它作为一期承诺。

**模板治理是 B 端后台的隐藏工作量。** 品牌方模板往往是 InDesign/Word 文件，AI 生成内容后的"套版"要么走结构化模板（推荐，但需要品牌方配合改造一次），要么走视觉还原（技术成本高）。这应该在 B 端后台作为一个明确的配置项。

## 三、两个议题的内在关系：产品知识库是枢纽

Yang Meng 在会议尾声把说明书生成"融合进 AI 售后服务项目"，Nandy 认同两者在产品知识学习上可以相互验证。这不是功能堆砌，而是业务流上的两个节点共用一个底座：

```
                 ┌──────────────────────────────┐
                 │        产品知识库（枢纽）        │
                 │  产品结构 / 零件 / 安装步骤 /    │
                 │  术语库 / 历史客诉 / 故障案例    │
                 └────────┬────────────┬────────┘
                          │            │
            写入 ◄────────┘            └────────► 读取
   ┌──────────────────┐                  ┌──────────────────┐
   │  AI说明书生成       │  ──验证/反哺──►  │  AI售后 Agent      │
   │  工厂/品牌方发起    │  ◄──高频问题──   │  C端客诉发起        │
   │  产品上市前         │                  │  产品上市后         │
   └──────────────────┘                  └──────────────────┘
```

说明书生成环节是知识库的**主要写入口**（产品上市前，工厂把结构化的产品知识录入系统）；售后 Agent 是知识库的**主要读取口**（产品上市后，用这些知识回答用户、生成维修指导）。反过来，售后沉淀的高频问题又能反哺说明书（FAQ 章节、警示语补充），形成闭环。这也回答了 Yang Meng 在会上没有得到正面回应的问题：售后知识中"产品结构类"的部分来自工厂（通过说明书流程进入），"案例类"的部分来自品牌方（通过历史客诉导入）。

## 四、AI Agent 系统各端实现路径

### 4.1 用户角色与端的对应关系

| 角色 | 定位 | 一期端形态 | 核心动作 |
|---|---|---|---|
| 终端用户（广义C端） | 客诉发起者 | 邮件（主）/ 二维码网页端（轻量）/ App（后置） | 发起客诉、补充信息、接收指导、评价 |
| 品牌方（售后负责人、销售团队） | 客诉管理主体、知识提供方 | PC 网页后台 + 邮件互通 | 配置环境、上传知识库、看仪表盘、接升级工单、邀请上下游、确认说明书 |
| 工厂销售 | 后端技术支持接口人 | 受邀加入 PC 网页端（受限视图） | 接工厂级升级工单、上传产品资料/中文说明书、邀请内部工程师 |
| 分销商/经销商 | 一线处理、可选参与方 | 受邀加入（受限视图）或不接入 | 查看订单相关客诉进度、回传处理结果 |
| 工厂售后/工程师/研发 | 工厂内部黑盒 | 一期不接入 | 由工厂销售在内部拉动 |

### 4.2 C端实现路径

**路径 A：邮件 Agent（一期主流）**

接管品牌方现有售后邮箱，对终端用户完全透明。技术要点：通过 IMAP/Gmail API/Microsoft Graph 授权接入；按发件人 + 主题线程 + 订单/序列号聚合成工单；解析正文和附件（照片 OCR、视频抽帧）；AI 根据知识库生成回复草稿；按置信度分流，高置信度自动回复，低置信度进人工审核队列；回复时自动翻译为用户语言并保留英文给服务端；所有往来写入工单时间线。首轮能力以文字为主。

**路径 B：二维码网页端（一期轻量入口）**

固定售后二维码印在说明书或产品标签旁，颗粒度到系列/型号。扫码进入 H5 表单，流程为：选语言 → 拍照上传产品标签（AI 识别 SKU/序列号，自动匹配订单、品牌、工厂）→ 描述故障（文字 + 照片）→ 进入 AI 实时对话。对话结束前引导留邮箱（把会话转为邮件工单以保留历史）或下载 App。网页端与邮件 Agent 共用同一工单系统和知识库，只是入口不同。无需登录，无需复杂视觉算法，用现有基座组合。

**路径 C：App（二期，承接留存需求）**

面向有紧急需求或需要历史记录的用户。承接网页端引流，提供工单历史、推送通知、视频/语音互动。会议明确一期不做，不强制下载。

**不做：社交媒体渠道**。token 成本与维护成本高，交由品牌方自行监控。

### 4.3 B端（品牌方）实现路径

PC 网页端，形态是"带对话框的智能体入口 + 传统后台功能"，并与邮件互通（关键事件邮件通知，可直接邮件回复驱动工单）。

功能模块按会议内容归纳为五块。**环境配置**：售后邮箱授权、品牌与产品线、二维码生成与下载（按系列/型号）、联系人与升级路由（谁接哪一级工单、SLA 时限）、支持语种、AI 自动回复的放行阈值。**知识库管理**：上传历史客诉记录、说明书、FAQ、术语表；对话式上传（直接把文件丢给智能体，由它结构化入库）。**工单与看板**：全部客诉的状态、响应时长、升级分布、高频故障、语种分布；周报自动生成并邮件推送。**上下游邀请**：按订单邀请工厂销售或分销商加入，授予该订单范围内的查看/处理权限。**说明书生成工作台**：上传模板、发起生成任务、审核与确认、下载交付。

品牌方的使用模式是"初期配置 + 定期看板"，因此后台的设计重点是配置向导的完整度和看板的信息密度，而不是日常操作效率。

### 4.4 工厂端实现路径

一期只对接工厂销售，形态是受邀加入 PC 网页端后的受限视图。工厂销售看到的是品牌方升级给工厂的工单，处理方式是在平台内回复（可附照片/视频/文档），或在内部用自己的方式解决后把结果回填。工厂销售拥有邀请权，可以把内部工程师或研发拉进具体工单协作。

工厂端的另一个入口是说明书生成：上传中文草版资料（含图纸、3D 模型），接收品牌方确认后的成品。

二期以后，工厂端增加备件建议（高频故障件清单）和免费配件进销存接管。

### 4.5 分销商端实现路径

一期不主动开发独立端，以受邀身份使用 PC 网页端的受限视图，查看与自己订单相关的客诉进度。需要补一个极轻的"事件打点"机制（扫码点一下"已处理"），用于解决信息孤岛问题，保证数据完整性。

### 4.6 Agent 核心层（各端共用）

各端只是入口，真正的能力在中台。按会议内容可以拆成以下组件：

| 组件 | 职责 | 对应会议决策 |
|---|---|---|
| 渠道接入层 | 邮件/网页/App 消息统一归一为工单事件 | 多渠道兼容、邮件为主 |
| 工单系统 | 工单生命周期、状态、时间线、SLA | 解决"进度难追踪" |
| 升级路由引擎 | AI 自判 → 追问 → 品牌方 → 工厂销售 | 三级升级机制 |
| 产品知识库（RAG） | 说明书、客诉案例、术语、零件结构的检索增强 | 知识由品牌方提供 + 工厂资料 |
| 图像识别服务 | 标签 OCR 识别 SKU/序列号；配件识别匹配安装步骤 | 固定码 + 拍照方案；视觉安装指导 |
| 多语言服务 | 用户语言 ↔ 服务端英语双向转换，术语约束 | 用户自选语言，够用就行 |
| 说明书生成引擎 | 模板套用、多语言文本生成、合规检查、3D 动画生成 | 说明书议题 |
| 数据分析层 | 高频故障、备件预测、跨品牌知识迁移 | 二期大数据与备件管理 |
| 权限与邀请模型 | 按订单的动态协作权限 | 邀请制链路 |

### 4.7 分期路线建议

**一期（MVP，先出 demo 再二创）**：邮件 Agent 接管品牌方售后邮箱；固定二维码网页端（选语言、拍标签识别、文字对话、留邮箱）；B 端 PC 后台的配置、知识库上传、工单看板；三级升级路由与邀请制；工单驱动的邮件通知。说明书生成做文本 + 多语言 + 模板套用的 demo，挑一个有 3D 模型的产品验证动画可行性。

**二期**：App 上线承接留存；视频/语音互动与实时翻译；说明书合规检查清单与术语库治理；3D 安装动画产品化；分销商事件打点。

**三期**：高频故障分析与备件备货建议；免费配件进销存接管与余量预警；跨品牌知识迁移；售后口碑数据的对外展示（工厂端"大众点评"）。

## 五、待决问题清单（建议下次会议对齐）

1. 售后知识的三个来源（品牌方历史客诉、工厂产品资料、平台通用经验）各自的录入责任人与格式要求。
2. AI 自动回复的放行阈值与审核规则：哪些类型的回复允许 AI 直接发出，哪些必须人工过目。
3. 分销商自行处理客诉时的数据回流机制，否则二期备件预测无数据基础。
4. 邮箱接管的具体技术路径（IMAP / Gmail API / Microsoft Graph）及品牌方的安全授权意愿。
5. 品牌方"升级工单接收人"的配置与 SLA：确认避免 AI 把工单升级回同一批文员。
6. 说明书生成的输入物最低要求（是否有 3D 模型、图纸格式）与目标市场合规清单。
7. 品牌方模板的结构化改造意愿（决定"套版"走结构化还是视觉还原）。
8. 二维码落地的真实扫码测试（回应 Nandy 对便捷性的疑虑）。
9. 一期 demo 的目标客户与产品：选一个有历史客诉数据、有 3D 模型的品牌/产品作为冷启动样本。
