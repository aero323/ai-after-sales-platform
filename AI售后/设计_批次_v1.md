# 批次（Batch）设计 v1

状态：待确认，未动代码。日期 2026-11-12。适用对象：`原型_品牌方后台.html`（单文件，当前唯一真相）、`src/engine.js`、`src/h5_app.js`、`原型_H5扫码端.html`。

本文回答四件事：批次是什么、数据放哪；产品管理怎么展示批次与订单；二维码按什么粒度生成、扫了之后发生什么；拆给子代理怎么执行、怎么验收。

---

## 0. 设计原则（沿用项目已确认的口径）

1. **逻辑写成真的**：批次的订单数、客诉数、客诉率从 `state.orders` / `state.tickets` 实时计算，不新增冗余计数字段，不做假数据。
2. **语义交给 LLM，规则留在引擎**：批次匹配、序列号解析、二维码批次与标签批次的一致性判断，全部是确定性规则，放 `src/engine.js`；不需要 LLM。
3. **一个来源**：批次代码只以序列号里的 `24B` 为准（`SN_RE` 第 2 段）。二维码、订单表单携带的批次都是"提示"，与序列号冲突时序列号优先并留痕。
4. **不改的一律不动**：工单状态机、说明书生成、政策层、知识图谱本次不碰。H5 视觉不改，只加参数解析。

## 1. 现状盘点（设计的事实基础）

- 订单 `state.orders[]`：`{ id:'PO-24118', product:'SM-900', qty, factory:'宁波力健机械', dealer, dealerCity, batches:['24B'], ship, warrantyUntil }`。**批次已经是订单上的一个字符串数组**，但没有独立实体。
- 序列号 `SM9-24B-00955` 由 `Engine.parseSerial()` 解析出 `{ product, batch:'24B', order, factory, dealer, city, warrantyUntil }`；订单按 `product + batches.includes(batch)` 反查。这是唯一权威链路。
- 工单 `ticket` 已有 `batch` 字段（建单时取订单 `batches[0]`），H5 桥接与后台收件都写入了。
- 供应商 = 合作方里的**工厂**（`state.partners` type=factory：宁波力健机械、东莞健步工业、青岛迈动器械、山东宝力龙）；当前只存在订单的 `factory` 字符串上，没有主数据。
- 二维码 `state.qrs`：**每型号一条** `{ scans, createdAt }`，URL 固定 `https://h5.ironpeak.support/s/<型号>`，页面上明确写了"同一型号所有批次使用同一个码，不需要一物一码"。本次要打破这条既有决定 → 保留"一型号一码"作为默认档，新增按批次 / 按供应商两档。
- 种子订单 9 张，涉及批次：SM-900 `24A/24B`、TR-650 `24A/24C`、RW-300 `24A/24B`、SM-700 `24A`、CB-1200 `25A`、F-C20 `25K` —— 共 6 个产品 9 个批次。CB-1200 的 25A 已有"孔距偏差"疑似批次问题（种子工单 `cb`，`suggest`），F-C20 的 25K 是 FWT-61 案例批次，这两个是现成的"批次异常"演示锚点。

## 2. 数据模型

### 2.1 新实体 `state.batches[]`

```js
{
  id:       'BT-SM-900-24B',     // product + code，稳定主键
  product:  'SM-900',
  code:     '24B',               // 与序列号第 2 段一致
  supplier: '宁波力健机械',       // 生产该批次的公司（partners 里 type=factory 的名字）
  po:       'PO-24118',          // 主订单（多订单时取最早一张）
  qty:      120,                 // 该批次总出货量（种子取主订单 qty，多订单累加）
  producedAt: <ts>,              // 生产日期（种子 = ship - 45 天，无来源时 null）
  shippedAt:  <ts>,              // 首次出货（取该批次最早订单 ship）
  note:     ''                   // 异常备注，如"孔距偏差，待工厂确认"
}
```

**键的选择**：只用 `code` 不行——`24A` 在 6 个产品里重复出现。所有查询一律 `(product, code)` 二元组，`id` 只是便捷字符串。

**不存派生值**：批次行上的订单数、客诉数、客诉率全部实时算：

```
batchOrders(b)      = state.orders.filter(o => o.product===b.product && o.batches.includes(b.code))
batchTickets(b)     = state.tickets.filter(t => t.product===b.product && t.batch===b.code)
batchComplaintRate  = batchTickets.length / b.qty        （qty 为 0 时显示 —）
batchRevenueHint    = Σ order.qty                        （展开行里的"出货 xx 台"用这个，比 b.qty 更可信）
```

**异常标记**（真规则，非随机；11-12 任务 A 实测绝对阈值会标出 7/9，改为相对规则）：
- `suspect`「疑似批次质量事件」：同批次 ≥2 条工单带 `t.suggest`（AI 聚集升级建议）。优先级最高。
- `attention`「重点关注」：同型号有 ≥2 个批次时，客诉率最高的那个批次，且其客诉率 ≥ 同型号最低批次客诉率 × 1.25，且客诉数 ≥ 3；同型号只有 1 个批次时退回绝对阈值（客诉 ≥3 且客诉率 ≥5%）。标记的 title 属性写出依据，如「客诉率 17.5%，是同型号最低批次（24A 10.0%）的 1.75 倍」。
- 种子效果：SM-900 24B、RW-300 24B 标 attention，其余不标。阈值常量 `Engine.BATCH_ALERT={minTickets:3, ratio:1.25, soloRate:0.05}`。

### 2.2 供应商

- 不新建供应商主表。`supplier` 是批次属性，取值来自 `partners`（type=factory）的名字；UI 下拉也只允许从这 4 家里选。
- 一致性规则：新建订单时 `order.factory` 与批次 `supplier` 不一致 → 订单保存**不阻止**，但在批次行与订单行各挂一枚 `<span class="tag amber">供应商不一致</span>`，点开显示差异。原型演示这个真实场景（同一批号换厂返工）。
- 一个供应商可有多个批次（宁波力健同时供 SM-900 24A/24B、TR-650 24A/24C、SM-700 24A）。

### 2.3 派生与同步

- `ensureBatches()`：启动时幂等重建——扫描 `state.orders`，为每个未登记的 `(product, code)` 生成批次（supplier=该订单 factory，po/qty/shippedAt 取首个订单）；已存在的只补空字段，不覆盖人工改过的 `note`。在 `boot()` 里 `syncEngineOrders()` 之后调用。
- `Engine.setBatches(list)`：镜像 `setOrders`，让 H5 与引擎也能按批次取供应商；`parseSerial` 的返回值追加 `supplier`（由批次表查，查不到退回订单 factory）。

## 3. 产品管理：批次视图

### 3.1 表格变化

在现有 10 列（11-12 版）里，`近 90 天客诉` 左侧插入一列 **批次**，内容 = `3 批次 ▾`（数字来自 `state.batches` 按产品计数）。其余列不动。

页头副标题改为：`产品档案与批次。点批次行展开看供应商、出货与客诉；点其他位置查看该产品的工单。`

### 3.2 展开行（行内，不跳页）

点击「批次 N ▾」在行下方插入占位行（`<tr class="batch-sub" data-for="SM-900">`，`colspan` 铺满），内部是子表：

```
┌ 批次 ┬ 供应商 ┬ 生产 ┬ 首次出货 ┬ 出货量 ┬ 订单 ┬ 客诉 ┬ 客诉率 ┬ 标记 ┬ 二维码 ┐
│ 24B  │ 宁波力健 │ 08-01 │ 09-14   │ 120 台 │ 1 张 │  7   │ 5.8%  │ 疑似批次质量事件 │ 已生成 412 扫 │
│ 24A  │ 宁波力健 │ 06-05 │ 07-20   │  90 台 │ 1 张 │  2   │ 2.2%  │ 重点关注 │ 已生成 96 扫 │
└──────┴─────────┴───────┴─────────┴────────┴──────┴──────┴────────┴──────┴─────────┘
  底部一行：3 个批次 · 2 家供应商 · 210 台在保 · 批次客诉合计 9 条
```

每行的交互：
- 点 **订单列**（`1 张`）→ **降级行为（用户 11-12 拍板）**：`go('orders')`，订单页按型号筛选（`orderProd=<型号>`），该批次徽章加 `sel` 高亮。**不做**按批次真筛选；此点在说明文档真/模拟清单里注明为"演示跳转，未按批次过滤"。
- 点 **客诉列** → `tf.prod; tf.batch=<代码>; go('tickets')`；工单页筛选器新增 `tf.batch`（`t.batch===tf.batch`），筛选条上显示"批次 24B ✕"可清除。
- 点 **二维码列** → `go('qr')` 并定位该产品卡片（滚动 + 高亮 600ms）。
- 展开状态存内存 `batchOpen={ 'SM-900':true }`，重新渲染保持；同时只允许一个产品展开（演示聚焦）。工厂角色可见（工厂要看自己的批次客诉），但订单列只显示与 `orderMembers` 可见的订单数——沿用可见范围规则，**不允许工厂看到别家工厂的批次行**：展开行按 `visibleBatches()` 过滤（brand 全部；factory 只含自己作为 supplier 的批次）。

### 3.3 空状态

产品没有任何批次（如刚新建的 EL-500 / CB-1200 若无订单）：批次列显示 `0 批次`，展开为空状态卡片：`这个型号还没有出货批次。批次从订单生成——新建或导入包含此型号的订单后自动出现。` + 「去建订单」按钮（`go('orders')`）。

### 3.4 二维码列在批次行里显示什么

该批次若存在 `scope='batch'` 的二维码记录 → `已生成 <scans> 扫`（点击跳二维码管理并聚焦）；只有产品级码 → `沿用型号码`；都没有 → `未生成`（品牌方可点，跳二维码管理并预选"按批次"档）。供应商级码同理显示在汇总行。

## 4. 二维码管理：三档粒度

### 4.1 数据结构变更

`state.qrs` 从 `{ 'SM-900':{scans,createdAt} }` 改为 `state.qrCodes[]`：

```js
{ id:'Q-0007', product:'SM-900', scope:'batch'|'supplier'|'product',
  scopeValue:'24B' | '宁波力健机械' | null,
  url:'https://h5.ironpeak.support/s/sm-900?q=Q-0007&b=24B',
  scans:412, createdAt:<ts>, printed:false }
```

迁移（`ensureQrCodes()`，boot 时跑，幂等）：旧 `qrs[p]` 有记录的 → 生成一条 `scope:'product'` 记录，`scans` 继承；`products[].qr=true` 仍保留为"该型号有任何码"的派生缓存，写入时同步。

### 4.2 产品卡片

每个产品卡片右上角加粒度切换（三选一分段控件，存 `state.qrMode[product]`，默认 `'product'` 与现状一致）：

- **一型号一码（默认）**：维持现状文案与行为。
- **按批次**：卡片主体变成批次列表，每行一个 QR 缩略 + 批次代码 + 供应商 + 扫描数 + 下载/打印；顶部一个「为全部未生成的批次生成」按钮。批次来源 `state.batches`。
- **按供应商**：按供应商分组，一家一条码；供应商来自该产品批次里出现过的 supplier。

二维码内容（URL 契约，H5 端将依赖它）：

```
https://h5.ironpeak.support/s/<product小写>?q=<二维码记录 id>
  按批次追加 &b=<code>
  按供应商追加 &f=<encodeURIComponent(供应商名)>
```

`q` 一定带（扫描归因）；`b`/`f` 是业务提示。本地原型里 `qrUrl()` 只用于展示与下载，预览按钮仍打开 `原型_H5扫码端.html?m=<型号>&go=chat…`，追加同样的 `b`/`f` 参数。

### 4.3 扫描数与归因

H5→后台桥接里 ticket 增加 `qr` 字段（来自 `?q=`）。后台导入 H5 工单时：`qrCodes.find(id).scans++`；找不到 `qr`（旧链接/一型号一码历史数据）→ 退回给该产品 `scope='product'` 的记录。工单详情头部显示小字 `来源码 Q-0007（SM-900 · 批次 24B）`，点击跳到二维码管理。

### 4.4 H5 端

- 解析 `?b=` / `?f=`：进入"拍标签"步骤前不改变任何流程（标签仍是主流程）；**只在序列号解析失败或用纯数字原始号时**，用 `?b=` 预填批次、`?f=` 预填供应商名，并在标签卡片批次一行标注 `来自二维码`（灰字）。序列号解析成功时，URL 批次不显示。
- **一致性检查（真规则，放 Engine**）：`Engine.checkBatchConsistency(serial, qrBatch)` → 若序列号有效且 `serial.batch !== qrBatch` → 返回 `{mismatch:true}`。H5 不打扰客户，静默把 `batchMismatch:true` 写进 ticket 桥接数据；后台建单时写入 `t.batchMismatch`，工单详情显示黄色提示：`扫码批次 24B 与标签批次 24A 不一致——可能贴错码或换批未换签`。
- H5 视觉、文案、步骤数不变；`h5test` 的 30 项应全部保持通过。

## 9. 子代理执行拆分（Opus）

文件现实：后台是**单文件**，引擎在 `src/engine.js`，H5 单文件由 `src/build.py` 只重建 H5 生成（`python3 build.py`，不要 `all`）。所以后台相关任务必须串行；H5 轨与后台轨并行；引擎改动先行且必须同时被两端消费，放在第一批。

依赖图：

```
A 引擎+数据层(engine.js + 后台 state/seed/boot + H5 单文件的 include?)
   └─┬─ B 产品管理批次视图（后台）
     └─ C 二维码管理三档 + scan 归因（后台，依赖 B 的样式类）
     └─ D H5 ?b/?f/q 参数（src/h5_app.js → build.py 只建 H5）
        └─ E 验收（batchtest + 回归 + 截图）
```

**A（串行，先做）**：`src/engine.js` 加 `checkBatchConsistency`、`BATCH_ALERT`、`setBatches`、`parseSerial` 返回 `supplier`；后台单文件里加 `BATCH` 小模块（`ensureBatches / Batch.of / Batch.orders / Batch.tickets / Batch.rate / visibleBatches`）、`SEED_VERSION='v7'`、种子批次、`qrCodes[]` 结构与 `ensureQrCodes` 迁移。产出：`node statetest.js` 通过，`domtest` 失败集合不变。备份先做：`备份_批次改动前_2026-11-12/`。
