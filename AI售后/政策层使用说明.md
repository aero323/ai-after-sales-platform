# 政策层 · 使用说明

> 一句话：**产品里所有的"判断"现在都在 `policy.config.json` 里，改文件 = 改行为，不用发版。**
> 代码只有 `src/policy.js` 一处读取它；页面、引擎、H5 都只调用 `Policy.xxx()`，不再出现魔法数字。

---

## 一、为什么做这件事

改造前，下面这些数字散在 4 个文件里：

| 判断 | 原来在哪 | 值 |
|---|---|---|
| 自动回复阈值 | engine.js `assess`、app_agent.js 意图、设置页 | 85 |
| 追问区间 | engine.js 里写死 `threshold-25` | 25 |
| 追问轮数 | app_state.js 写死 `>=2` | 2 |
| 无匹配封顶 | engine.js `NO_MATCH_CAP` | 45 |
| 寄件免确认线 | engine.js `<=50`、app_state.js 文案 `>50`、app_pages.js 提示 `>50` | 50 美元 |
| 一级/二级时限 | app_state.js、app_pages.js 约 12 处 | 4h / 24h |
| 关闭后重开窗口 | app_state.js 写死 `7*DAY` | 7 天 |
| 自修跟进窗口 | app_state.js 写死 `2*DAY` | 2 天 |
| 批次聚集 | app_state.js 写死 `>=3 && >=2×` | 3 起 / 2 倍 |
| 运单催办 | app_pages.js / app_state.js 写死 `24*HR` | 24 小时 |

现在全部收到 `policy.config.json`，每项带 说明 / 依据 / 可改范围 / 锁定标记。

## 二、结构

```
src/policy.config.json   ← 唯一事实来源（业务可读，带注释字段 _说明/_依据）
src/policy.js            ← 读取、校验、审计、四个决策函数
src/build.py             ← 构建时把 config 内容内联进 policy.js（保持单文件原型）
```

运行时取值顺序：

```
Policy.get('routing.l1.hours')
  → state.policy.values（产品经理在设置页改过的）
  → adminState.policy.values（H5 端从本地存储读到后台的改动）
  → policy.config.json 的出厂值（构建时内联）
```

## 三、在设置页怎么用

系统设置 → **AI 回复规则**（这一页现在就是政策面板）：

1. 每项显示名称、当前值、可设范围、单位、修改依据；已改动的项标"已改（出厂 xx）"，可单项恢复。
2. 阈值下面实时回放：按当前政策，近 30 天工单里 AI 直答 / 先追问 / 转人工各占多少、多少条会自动承诺寄件。
3. 底部"变更记录"：谁、什么时候、把哪项从多少改到多少，最多保留 200 条，可导出 JSON。
4. "全部恢复出厂值"一键回到 `policy.config.json` 的初始状态。

所有修改即时生效并写入浏览器本地存储（`state.policy`），刷新不丢；点"重置演示数据"会连同政策一起恢复出厂。

## 四、代码怎么用

```js
// 普通取值（带出厂值兜底）
Policy.get('routing.l1.hours')            // → 4

// 修改（带范围校验；锁定项会抛错）
Policy.set('autoReply.threshold', 80);    // {changed:true, from:85, to:80}，自动记审计

// 兼容旧入参的对象（engine / H5 用）
Policy.view()                             // {threshold, rules:{}, promise:{}, askBand, ...}

// 派生量
Policy.slaHours('l1')                     // 4
Policy.trackingMs()                       // 24h 毫秒
Policy.isBatchHot(same, others)           // 批次聚集判定

// 决策（LLM 化之后 Proposal → Decision 的唯一入口）
Policy.mustEscalate(proposal, facts)      // 安全件 / 要求真人 / 追问用尽 → 必须转人工
Policy.canAutoReply(proposal, facts)      // 证据 + 阈值 + 规则 → 能否直答 / 追问 / 转人工
Policy.canShip(issue, facts)              // 金额上限 + 开关 + 库存 → 能否自动承诺
Policy.decide(proposal, facts)            // 合成 {action, status, ship, slaHours}
```

`engine.js` 的 `assess()` 已改为读 `Policy`，传入的 `settings` 仍兼容（Node 测试和 H5 没有 `state` 时用），但优先走政策层。对外 API 签名不变。

## 六、改动前需要知道的

1. **config 里的 `_...` 开头的键不是配置**，是说明和依据，页面会显示它们，代码忽略它们。
2. **改 `threshold` 不会改变已有工单的置信度**。置信度是建单时算的，改阈值只影响新工单和"回放比例"的展示。
3. **`b2b` 默认是关的**，这是会议里"B 端也是客户"的取向；打开后企业邮箱来信一律转人工。
4. **锁定项的"双签"目前是约定，不是技术强制**——改 config 文件重新构建就能生效。正式版建议加一条 CI 检查：`autoCommitLimitUsd` 或 `bigParts` 的 diff 必须附带第二个人的审批记录。
5. **这层不替代 LLM 改造**。政策层管"公司答应什么"，LLM 管"客户在说什么"；两者在 `Policy.decide(proposal)` 交接（见《LLM嵌入方案》§4、§7）。

## 七、触发词表（2026-11-05 追加）

改造前，“什么话算触发硬规则”是 `engine.js` 第 125–128 行的四组正则，业务侧看不到也改不了。现在全部移进 `policy.config.json` 的 `hardRuleWords`，判定统一走 `Policy.matchesHardRule(rule, text, email)`。

**设置页 → AI 回复规则 → “触发词表”** 每组规则显示：

- 近 30 天触发次数，以及命中最多的是哪几个词（按次数排序）；
- 最近三条例子的原句节选和命中的词——这是发现误杀最快的方式（比如 “cable” 把 “cable tv” 也抓进来，会把这个词删掉或改成更精确的写法）；
- 词条以 chip 形式列出，点 × 删除，输入框回车添加。

**伤害描述词锁定**：`safety.injury` 里的 31 个词（受伤 / 砸 / 触电 / 断裂 / 塌 / 儿童无人 / children alone / injur / collapse / verletz / gerissen 等）在页面上带 🔒，增删都会弹出“需技术与业务双签”。理由是这条规则失效的方向不安全——误杀代价是 4 小时响应，漏杀代价是伤人事故。安全部件名（`safety.parts`）不锁，随产品线增删。

**几条使用注意**：

1. 词表是**子串匹配、大小写不敏感**，和原正则是同一语义（宁可多抓）。写短词要小心：“burn” 会命中 “burner”，“return” 会命中 “return policy”。
2. 改词表**只影响之后的新来信**。已建工单的 `reasons` 是当时算的，不会重算——页面上的命中统计反映的是“当时的词表”，改完要等几天才看得出效果。
3. 词表命中只决定“是否转人工”，不决定“是不是安全问题”。转人工之后由人判断；安全件的固定警告句仍写在知识条目里，不受词表影响。
4. b2b 是**反向判定**：邮箱不在白名单里就算企业邮箱。白名单里加一个域名，等于把那个域名的客户当普通客户处理。
